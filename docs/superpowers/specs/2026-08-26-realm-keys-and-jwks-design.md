# Phase 1, slice 2: realm signing keys, the signer port, and the JWKS endpoint

Status: design approved in conversation, not yet implemented
Branch: `feat/realm-keys-and-jwks`

## What this slice is

Slice 1 created the `realms` table and seeded the master realm, which gave every
realm an `issuer` and nothing to back it with. An issuer is half of a trust
root; the other half is a key. OIDC defines a user's identity as the pair
`(iss, sub)`, and a client walks `iss` → discovery → `jwks_uri` → key by `kid` →
signature. This slice builds that key half.

It ends with: a `realm_keys` table across the four dialects, a key aggregate
whose private material is encrypted at rest with a master key the process reads
from the environment, an active RS256 and an active ES256 key for every realm
created from now on — the master realm included, seeded on boot — a
`SignerSource` port that hands out a `crypto.Signer` for a realm, a public JWKS endpoint per
realm, and an `aegisd key` subcommand to operate all of it without a server
running.

Nothing signs a token yet. That is slice 4.

## What this slice is not

Named because each was left out deliberately, not forgotten:

- **No discovery document.** In this slice there is no `authorization_endpoint`,
  no `token_endpoint` and no `userinfo_endpoint` to advertise, and a discovery
  document that lies about what the server supports is worse than no document.
  It arrives with the endpoints, and brings with it the route trap already
  recorded in slice 1: OIDC Discovery *appends*
  (`{issuer}/.well-known/openid-configuration`) while RFC 8414 *inserts*
  (`/.well-known/oauth-authorization-server/{path}`) — two different documents,
  and eventually both have to be served.
- **No `default_signature_alg` column on `realms`.** Nothing signs in this
  slice, so the column would have no consumer for two slices. `SignerFor` takes
  the algorithm as a parameter. Adding a column later is cheap; carrying a dead
  one is not.
- **No key expiry and no automatic rotation.** Rotation is an operator action
  here. Automatic rotation needs a per-realm schedule, which needs somewhere to
  configure it, which is the admin API.
- **No encryption keys.** JWE — encrypted ID tokens, encrypted request objects —
  needs a key with `purpose = 'enc'`. The column exists and admits only `'sig'`;
  see "`purpose` exists now and holds one value".
- **No key import.** Every key in this slice is generated by aegis. Importing a
  customer's existing key pair is an admin API operation and brings its own
  validation surface.
- **No `x5c`, no certificates.** aegis does not issue certificates for signing
  keys. Keycloak does; nothing in JWS or JWK requires it.
- **No signer cache.** See "No cache, deliberately".
- **No admin HTTP surface for keys.** Slice 5 for the API, slice 6 for the
  console. The CLI in this slice is a thin adapter over the same service those
  will call.

## Decisions this slice implements

Each was closed in conversation before a file was written. They are recorded
here because the reasoning does not survive in the code, and because the schema
half of them cannot be reversed after the first on-prem installation.

| Area | Decision |
|---|---|
| Boundary | Keys, the signer port and JWKS. No discovery document |
| Algorithms | RS256 (RSA-2048) and ES256 (P-256), both implemented now |
| Active key | One per `(realm, purpose, algorithm)` — the Keycloak model |
| Encryption at rest | A per-installation master key from the environment, AES-256-GCM over the PKCS#8 |
| Master key delivery | `AEGIS_CRYPTO_MASTER_KEY`, with a `_FILE` suffix accepted; never a YAML key |
| KEK identity | `kek_id` derived from the key material, never configured |
| Associated data | `realm_id ‖ kid`, so a row copied to another realm does not open |
| Port shape | `SignerFor` returns a `crypto.Signer` plus `kid` and `alg` |
| Key identifier | `kid` is the RFC 7638 thumbprint of the public key |
| Uniqueness | A unique index over a nullable marker column, not a table constraint |
| JWKS route | `/realms/{slug}/protocol/openid-connect/certs`, Keycloak-compatible |
| Operations | `aegisd key list\|rotate\|disable\|enable\|rewrap`, each a thin call into `KeyService` |
| Realm creation | Realm and its keys in one transaction; generation outside it |

`internal/handler/oidc` sits beside `internal/handler/page`, at the same depth,

## The schema

Four migrations per dialect, one statement per file as the existing rule
requires.

### `0002_create_realm_keys`

Postgres:

```sql
CREATE TABLE realm_keys (
    id            uuid           NOT NULL,
    realm_id      uuid           NOT NULL,
    kid           varchar(64)    NOT NULL,
    purpose       varchar(8)     NOT NULL,
    algorithm     varchar(8)     NOT NULL,
    status        varchar(16)    NOT NULL,
    active_marker char(1)        NULL,
    public_key    varchar(1024)  NOT NULL,
    private_key   varchar(4096)  NOT NULL,
    kek_id        varchar(64)    NOT NULL,
    created_at    timestamptz(6) NOT NULL,
    updated_at    timestamptz(6) NOT NULL,
    CONSTRAINT pk_realm_keys PRIMARY KEY (id),
    CONSTRAINT fk_realm_keys_realm FOREIGN KEY (realm_id)
        REFERENCES realms (id) ON DELETE CASCADE,
    CONSTRAINT ck_realm_keys_purpose   CHECK (purpose IN ('sig')),
    CONSTRAINT ck_realm_keys_algorithm CHECK (algorithm IN ('RS256', 'ES256')),
    CONSTRAINT ck_realm_keys_status    CHECK (status IN ('active', 'passive', 'disabled')),
    CONSTRAINT ck_realm_keys_marker    CHECK ((status = 'active') = (active_marker IS NOT NULL))
);
```

The per-dialect deltas are the ones slice 1 already established: `uuid` becomes
`CHAR(36)` on MySQL and MariaDB, `timestamptz(6)` becomes `DATETIME(6)` there,
and the MySQL family carries `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
COLLATE=utf8mb4_bin ROW_FORMAT=DYNAMIC`.

**On SQLite every column above becomes `TEXT`** — `uuid`, `varchar(n)`, `char(1)`
and `timestamptz(6)` alike. The table is `STRICT`, and a `STRICT` table admits
only `INT`, `INTEGER`, `REAL`, `TEXT`, `BLOB` and `ANY`; a `varchar(64)` there is
not a wider `TEXT`, it is a DDL error. `0001_create_realms` already looks like
this, and the length limits therefore exist on three engines out of four. That is
not new and not worth solving here: the aggregate validates on the way in through
`Rehydrate`, which is what a customer's DBA writing directly is checked by.

### `0003`, `0004`, `0005` — the indexes

```sql
CREATE UNIQUE INDEX uq_realm_keys_kid    ON realm_keys (realm_id, kid);
CREATE UNIQUE INDEX uq_realm_keys_active ON realm_keys (realm_id, purpose, algorithm, active_marker);
CREATE        INDEX ix_realm_keys_lookup ON realm_keys (realm_id, status);
```

`ix_realm_keys_lookup` is also the foreign key's index. Postgres does not index
a foreign key column on its own and InnoDB does, so it is declared in all four
directories rather than left to the engine — the rule slice 1 set, and the
reason a `DELETE` on the parent stays O(log n) on the customer's Postgres.

### Why the uniqueness lives in an index and not a table constraint

`realms` declares its unique rules as named table constraints. `realm_keys` does
not, and the difference is deliberate: SQLite has no `ALTER TABLE DROP
CONSTRAINT`. Changing a named constraint there means creating a new table,
copying the rows, dropping the old one and renaming — four statements, four
files, on a table holding live key material. A unique index is `DROP INDEX` plus
`CREATE INDEX` on all four engines.

The rule that is most likely to need changing is exactly this one: it changes
the day `purpose` admits `'enc'` in a different shape, or the day the active key
stops being per algorithm. So it is written in the form that can be changed.

`realms` is left as it is. Rewriting it now buys nothing.

### `active_marker`, and why the obvious solution is not portable

"One active key per `(realm, purpose, algorithm)`" is naturally a partial index:

```sql
CREATE UNIQUE INDEX ... ON realm_keys (realm_id, purpose, algorithm)
    WHERE status = 'active';
```

Postgres supports it. SQLite supports it. **MySQL and MariaDB have neither
partial nor filtered indexes**, and a functional index over an expression
yielding NULL is not the same thing. Since the schema has to be the same rule on
four engines, the rule moves into a column: `active_marker` holds `'y'` when the
row is active and `NULL` otherwise, and the unique index covers it.

The load-bearing property is that **NULLs do not collide in a unique index** on
any of the four — Postgres treats them as distinct by default, InnoDB and
MariaDB allow repeated NULLs in a unique index, and SQLite does the same. This
is a premise, and slice 1 already learned what an unverified four-engine premise
costs, so there is an integration test whose only job is to prove it. See
"Testing".

`ck_realm_keys_marker` keeps the marker from lying: the boolean equality forces
`active_marker IS NOT NULL` to hold exactly when the status is `active`. Both
sides of the comparison are non-nullable expressions, so the check never
evaluates to NULL and never passes by accident. It is valid on all four —
Postgres compares booleans directly, the MySQL family and SQLite compare the
0/1 they evaluate to.

### `kid` is a thumbprint

The `kid` is the **RFC 7638 JWK thumbprint** of the public key: the canonical
JWK containing only the required members, lexicographic key order, no
whitespace, SHA-256, base64url without padding — 43 characters.

Deterministic beats random here. The same key always yields the same `kid`, so
importing a key twice collides on `uq_realm_keys_kid` instead of producing two
identities for one key, and a `kid` in a token can be matched against a key
recomputed from scratch. `varchar(64)` leaves room for a longer thumbprint if a
future algorithm brings one.

Required members per family, and nothing else in the thumbprint input:

- RSA: `e`, `kty`, `n`
- EC: `crv`, `kty`, `x`, `y`

### `purpose` exists now and holds one value

`CHECK (purpose IN ('sig'))` is the whole domain of the column today. It is
present anyway because it participates in `uq_realm_keys_active`, and adding a
column to a unique index later means dropping and recreating that index in four
directories. One `varchar(8)` now costs less than that later.

When JWE arrives, the migration is one `CHECK` swap and no index work.

### Key material as base64 text

`public_key` holds the SPKI DER of the public key, base64. `private_key` holds
`nonce ‖ ciphertext ‖ tag` from AES-256-GCM over the PKCS#8 DER, base64.

Text rather than `bytea`/`varbinary`/`BLOB` for the same reason UUIDs are text:
a readable dump, no per-driver binary handling, no `bytea` hex escaping in a
`pg_dump` the customer's DBA opens. The 33% overhead is on rows measured in
kilobytes, a dozen per realm.

The lengths are not arbitrary. MySQL checks a **65,535 byte limit on the
declared row size** at DDL time, and under `utf8mb4` each declared character
counts as four bytes. With `public_key varchar(1024)` and `private_key
varchar(4096)` the declared row is roughly 21 KB, which leaves the table room to
grow columns later. It also sets a ceiling worth naming: 4096 base64 characters
hold about 3 KB of sealed material, which fits an RSA-4096 PKCS#8 with room to
spare and does not fit RSA-8192. Neither is generated by this slice; the ceiling
matters the day key import exists.

### Reserved words

The table is `realm_keys` and not `keys` because `KEYS` is reserved in MySQL.
The column is `purpose` and not `use` or `usage` because `USAGE` is reserved
there too. Neither would break Postgres or SQLite, which is precisely how a name
like that survives review and fails on one engine.

### Engine version floors are unchanged

Slice 1 already set MySQL 8.0.16 as the floor because named `CHECK` constraints
were silently ignored before it. Nothing here moves any floor: unique indexes
over nullable columns, `char(1)`, and boolean comparison inside `CHECK` are
available at every floor already declared.

## The domain

### `internal/domain/key`

A new package beside `internal/domain/realm`, under the same rule: nothing
outside the standard library and `github.com/google/uuid`.

```go
type Key struct {
    id        uuid.UUID
    realmID   uuid.UUID
    kid       string
    purpose   Purpose
    algorithm Algorithm
    status    Status
    publicKey crypto.PublicKey
    sealed    []byte
    kekID     string
    createdAt time.Time
    updatedAt time.Time
}
```

Private fields with accessors, no setter for `id`, `realmID`, `kid`, `purpose`
or `algorithm` — the same shape `realm.Realm` uses to make the issuer immutable
by compiler rather than by memory.

Two doors, like the realm has:

- `New(realmID, purpose, alg, publicKey, sealed, kekID)` is birth. It generates
  the UUIDv7, derives the `kid` from the public key, stamps both timestamps to
  the same UTC instant, and validates.
- `Rehydrate(...)` is the repository's way back in. It takes the stored `kid` as
  given rather than recomputing it, for the reason `realm.Rehydrate` takes the
  stored issuer: recomputing an identity on every read is how the stored value
  and the derived value drift apart without a symptom.

`New` refuses a nil `realmID`, an unknown algorithm or purpose, a public key
whose type does not match the algorithm — an RSA key declared `ES256` — and
empty `sealed` or `kekID`. `Rehydrate` refuses the same, plus an unparseable
status and an empty `kid`. Neither validates that the sealed blob opens: the
domain has nothing to open it with, and that is on purpose.

### The aggregate holds sealed bytes it cannot read

`sealed` is opaque to the domain. `key` imports no cipher, knows no master key,
and has no method that returns plaintext private material. Encryption is a
service-level concern satisfied by infrastructure, and keeping it out of the
aggregate is what makes the domain testable without a key and what keeps a
future KMS from having to fit inside a domain type.

The public key is held parsed, as a `crypto.PublicKey`, because the thumbprint
and the JWK projection both need it and parsing it once at construction beats
parsing it per JWKS request.

### The JWK projection lives here

`Key.JWK()` returns the public JWK — `kty`, `kid`, `alg`, `use`, and `n`/`e` or
`crv`/`x`/`y`. It belongs to the domain because the thumbprint already forces
the canonical JWK to be built here, and two constructions of the same object in
two packages is the pair that eventually disagrees.

The `{"keys":[…]}` envelope, the content type, the ordering and the cache
headers are not domain. They are the handler.

Two encoding traps, both of which produce a JWKS that looks right and verifies
nothing:

- **RSA `n` is minimal big-endian**, base64url, no padding, no leading zero
  byte. `e` is the same and is almost always `AQAB`.
- **EC `x` and `y` are fixed-width**, left-padded with zeros to the curve's
  field size — 32 bytes each for P-256. Trimming a leading zero byte because it
  looks like a leading zero is the classic bug here; `big.Int.Bytes()` trims it
  for you.

### Status transitions, and the invariant

```
active  → passive     (what rotation does to the outgoing key)
passive → disabled    (leaves the JWKS)
disabled → passive    (comes back into the JWKS)
```

An **active key cannot be disabled directly**. The transition does not exist on
the aggregate, so the compiler and not a reviewer is what prevents a realm from
ending up with no active key and nothing able to sign. Revoking a compromised
key is `rotate` and then `disable`, which is the correct order anyway: the
replacement exists before the old one stops being published.

`disabled → active` does not exist either. Bringing a key back into service is a
rotation.

The methods are `Deactivate()`, `Disable()` and `Enable()`, each refusing with
`ErrInvalidTransition` from any status the table above does not list. There is
no `Activate()`: a key becomes active only by being born active, which is what
makes `Create` the only writer of `active_marker`.

`ParseAlgorithm`, `ParsePurpose` and `ParseStatus` exist for the same reason
`realm.ParseStatus` does — the repository rehydrates from text columns a DBA can
write into.

### Errors

Declared in the package, in the shape `realm` already uses, so the layers that
have to recognise them do not import the repository:

- `ErrNotFound` — `FindByKID` found nothing
- `ErrNoActiveKey` — `FindActive` found nothing. Separate from `ErrNotFound`
  because the callers differ: `SignerFor` turning up empty is a realm that
  cannot sign, while `Rotate` turning up empty is normal and means there is
  nothing to deactivate
- `ErrActiveKeyExists` — `uq_realm_keys_active` fired
- `ErrKIDTaken` — `uq_realm_keys_kid` fired
- `ErrUnsupportedAlgorithm`
- `ErrInvalidTransition`

## Encryption at rest

### Why there is a master key at all

Keycloak does not have one. Realm signing keys live in `COMPONENT_CONFIG` as
base64 DER in plain text, and the answer to confidentiality is delegated
downward to disk and database encryption. Their `java-keystore` provider moves
the material to a file but leaves the keystore password in the same plaintext
table.

aegis runs on-prem, in the customer's own database, and `SELECT * FROM
realm_keys` is the first query anyone with read access runs. Zitadel is the
precedent for the other choice: a 32-byte master key from the environment, no
master key no boot.

The failure mode this introduces is real and bounded, and the bound is why it is
acceptable: **losing the master key loses no data.** Signing keys are
regenerable. The recovery is to generate new ones per realm and let clients
refetch the JWKS; live access tokens are unverifiable for their remaining
lifetime, which is minutes. That is a short outage, not a loss.

### Configuration

A new section in `internal/configs`:

```go
type Crypto struct {
    MasterKey         string `yaml:"-"`
    MasterKeyPrevious string `yaml:"-"`
}
```

The whole section is tagged out of YAML on `Application` as well, so a `crypto:`
key in the configuration file fails the boot the way a `password:` under
`database` already does. `aegis.example.yaml` documents its absence in the same
voice the database password is documented in.

Environment variables follow the section-prefix convention the file already
uses:

```
AEGIS_CRYPTO_MASTER_KEY=
AEGIS_CRYPTO_MASTER_KEY_FILE=/run/secrets/aegis-master-key
AEGIS_CRYPTO_MASTER_KEY_PREVIOUS=
AEGIS_CRYPTO_MASTER_KEY_PREVIOUS_FILE=
```

The `_FILE` suffix is the pattern for a mounted Docker or Kubernetes secret, and
it is strictly better than the variable: outside `/proc/<pid>/environ`, outside
`kubectl describe` on a manifest with an inline `value:`, and not inherited by a
subprocess. It is a read, not a write, so nothing about it conflicts with the
read-only root filesystem of the `distroless/static` image.

**Setting both forms of the same secret is a boot error**, not a precedence
rule. Ambiguity about which secret is in use has to fail loudly.

`envtools` gains `LookupSecret(key string) (string, bool, error)` beside its
existing lookups, since this is the second place that will want it — the first
admin bootstrap in slice 5 is the other.

### `applyEnv` gains an error

Reading a file can fail, and today `applyEnv(cfg)` returns nothing. It becomes
`applyEnv(cfg) error`, and `WithEnv` joins it:

```go
b.err = errors.Join(b.err, applyEnv(b.cfg))
```

That is the whole change, and it puts a missing secret file in the same
aggregated report as every other configuration problem, which is what `Build`
exists to produce.

### Validation, and where the development fallback is installed

The section joins the existing machinery rather than inventing its own:
`defaultCrypto()` in `Default()`, an entry in `sections()`, and
`Validate(profile Profile) error` — the signature `TLS` and `Database` already
have, because the rule depends on the profile.

**The development fallback belongs to `Normalize`, not to `Validate`.**
`Crypto.normalizeForDevelopment()` installs the constant when the variable is
absent, beside `TLS.normalizeForDevelopment()` and
`Database.normalizeForDevelopment()` in the block `Normalize` already guards
with `if !cfg.Profile.IsDev()`. Validation then has one job in both profiles:
the value is base64 that decodes to exactly 32 bytes. A fallback installed
inside validation would make the value depend on the order validators run in.

The failure message says how to produce a key — `openssl rand -base64 32` —
because it is the operator's first contact with the concept.

### Behaviour by profile

The same shape as the TLS certificate generated in memory and the issuer
re-derived on boot, both of which already diverge by profile:

- **Development**: with no variable set, a documented constant is used, and a
  `WARN` naming it is logged on every boot. Tilt and `make dev` keep starting
  with no setup, and development data is disposable.
- **Production**: refuses to boot without the variable. It **also refuses when
  the value equals the development constant**, which is the only thing that
  keeps the convenience from being inherited into production in silence. That
  check belongs to `Validate`, where the profile is in hand.

### `kek_id` is derived, not configured

```
kek_id = hex(SHA-256("aegis:kek:v1" ‖ key)[:16])
```

An operator-chosen identifier can lie. Rotate the key material without changing
the label and every row claims to be openable by a key that does not open it.
Derived, it cannot: changing the key changes the id, and the domain separation
prefix keeps the value from being a bare hash of the secret.

### The `Sealer` port

Declared in `internal/service` because that is where it is consumed, and
implemented by `internal/infra/sealer`, which does not import the interface —
the same arrangement `CertificateSource` has in `application/ports.go`.

```go
type Sealer interface {
    Seal(plaintext, aad []byte) (sealed []byte, kekID string, err error)
    Open(sealed, aad []byte, kekID string) ([]byte, error)
}
```

The implementation holds the current key and, when configured, the previous one.
It **seals with the current key always** and **opens with whichever key matches
the row's `kek_id`**. That is what makes a rewrap possible while the service is
serving traffic: old replicas and new replicas read the same rows throughout.

`Open` with an unknown `kek_id` is an error naming the id, not a decryption
attempt.

AES-256-GCM, 12-byte random nonce stored as the blob's prefix. Random nonces
are safe here by a wide margin — the birthday bound is around 2^32 seals under
one key, and this table sees a handful of writes per realm per year.

### Associated data binds the ciphertext to `(realm_id, kid)`

The AAD is `realm_id ‖ kid`. A row copied into another realm does not open,
which matters in a product whose worst failure is leakage across the tenancy
boundary.

It is `kid` and not the row's `id` for a mechanical reason: `id` is generated by
`key.New`, and `key.New` needs the sealed blob to construct the aggregate. The
`kid` derives from the public key and therefore exists before either. It binds
just as tightly, since it is a hash of the very key being sealed.

### Rewrap

`aegisd key rewrap` runs with both variables set. For each row whose `kek_id` is
not the current one: open with the previous key, seal with the current, write
`private_key`, `kek_id` and `updated_at`.

It is **not one transaction**, and that is the point of the column. Every row
states which key opens it, so an interrupted rewrap leaves the database
consistent and the command is resumable: running it again continues where it
stopped, and running it after it finished does nothing.

## Persistence

### `realmKeyRecord`

The same two-type arrangement slice 1 established — a pure aggregate and a GORM
record, no `gorm` type tags, because the migrations define the columns and a tag
would be a second description of them.

`toDomain` goes through `key.Rehydrate`, which validates, for the reason already
written in `realm_record.go`: a customer's DBA writes here directly. Time columns
use the package's `Timestamp` type, which is what survives SQLite handing a
`TEXT` column back as a string.

**`active_marker` has no field on the aggregate.** It is derived by `fromDomain`
— `'y'` when the status is active, `NULL` otherwise — because it is not a fact
about a key, it is the mechanism that makes one rule enforceable on four
engines. Putting it on the aggregate would let a caller set it, and the whole
point is that nobody can.

### `translate` has to learn there is a second aggregate

`repository.translate` currently maps `gorm.ErrRecordNotFound` to
`realm.ErrNotFound` unconditionally. With a second aggregate that is wrong. It
becomes `translate(err error, notFound error) error`, each call site passing its
own, and the constraint-name switch gains the three new names:
`uq_realm_keys_kid`, `uq_realm_keys_active`, and the SQLite spelling, which
names columns rather than constraints — `realm_keys.kid` and
`realm_keys.active_marker`.

The SQLite branch matters more here than it did for realms: `active_marker` is
the column SQLite will name when two replicas race to seed, and a race that
surfaces as an untranslated driver error would fail a boot instead of resolving
into a re-read.

### `Store` gains `Keys()`

```go
type Store interface {
    Realms() RealmRepository
    Keys()   RealmKeyRepository
    InTx(ctx context.Context, fn func(Store) error) error
}
```

`InTx` is unchanged and still the only place a transaction begins.

### `RealmKeyRepository`

```go
type RealmKeyRepository interface {
    Create(ctx context.Context, k *key.Key) error
    FindActive(ctx context.Context, realmID uuid.UUID, purpose key.Purpose, alg key.Algorithm) (*key.Key, error)
    FindByKID(ctx context.Context, realmID uuid.UUID, kid string) (*key.Key, error)

    // Ordered id descending. Deterministic on all four engines, and
    // chronological, because the id is a UUIDv7. See "The document".
    ListByRealm(ctx context.Context, realmID uuid.UUID, statuses []key.Status) ([]*key.Key, error)

    // Writes status, active_marker and updated_at, and no other column.
    Update(ctx context.Context, k *key.Key) error

    // Writes private_key, kek_id and updated_at, and no other column.
    // Separate from Update because sealed material is immutable outside a
    // rewrap, the same reasoning that keeps Reissue separate on realms.
    Rewrap(ctx context.Context, k *key.Key) error

    // For the rewrap command: rows not sealed under kekID, across every
    // realm, capped at limit. No cursor, because a row leaves this set the
    // moment it is rewrapped: asking again from the start both terminates and
    // resumes.
    ListStaleKEK(ctx context.Context, kekID string, limit int) ([]*key.Key, error)
}
```

## The service

### `KeyService`

```go
func NewKeyService(store Store, sealer Sealer, generator KeyGenerator) *KeyService
```

### `KeyGenerator`

```go
type KeyGenerator interface {
    Generate(alg key.Algorithm) (signer crypto.Signer, pkcs8 []byte, err error)
}
```

It does not return the SPKI of the public key. `Key.PublicKeyDER()` marshals it
from the parsed key the aggregate already holds, and two producers of the same
bytes is a pair that can disagree.

A port rather than a direct call into the standard library for one concrete,
non-speculative reason: without it every service unit test pays a real RSA-2048
generation. Implemented by `internal/infra/keygen`, which is where the
parameters live — RS256 is RSA-2048, ES256 is P-256. Key size is not
configurable in this slice.

### `Prepare` and `persist`, and why generation is outside the transaction

```go
// No context and no database: CPU and sealing only.
func (s *KeyService) Prepare(realmID uuid.UUID, algs ...key.Algorithm) ([]*key.Key, error)

// Inside a caller's transaction.
func (s *KeyService) persist(ctx context.Context, st Store, keys []*key.Key) error
```

Generating RSA-2048 takes on the order of 100–300 ms. Holding a database
transaction open across it is the thing not to do, and the split is what avoids
it while keeping the insert atomic.

`Prepare` generates, seals with `realm_id ‖ kid` as AAD, and builds the
aggregates. It touches nothing external except the entropy source.

### `RealmService.Create` becomes atomic over three rows

```
1. realm.New(...)                            no database
2. keys.Prepare(realm.ID(), RS256, ES256)    CPU and sealing, no database
3. InTx {
       Realms().Create(realm)
       Keys().Create(k) for each key
   }                                         three inserts, milliseconds
```

`RealmService` holds a `*KeyService`, so `NewRealmService` gains a parameter.
The alternative — a third service whose only job is to call two others in
order — is a layer for a three-step sequence.

This is what makes a realm without keys unrepresentable, which is what made
`pending` an impossible status back in slice 1. A realm exists or it does not;
there is no window in which it exists and cannot sign.

### `EnsureMaster` ensures keys too

The seed reads the master realm's active keys first and generates only what is
missing. Without the read, every boot burns two key generations to discard them.

The race between replicas resolves the way the realm seed already resolves its
own: both replicas find nothing, both generate, both insert, and
`uq_realm_keys_active` rejects one. The loser translates the violation into
`key.ErrActiveKeyExists`, re-reads, and discards what it generated — the same
shape as the `ErrSlugTaken`/`ErrIssuerTaken` fall-through already written in
`EnsureMaster`, and for the same reason: migration holds a session lock, the
seed does not.

The seed touches keys only when a key is missing. It never rotates, never
disables, and never reconciles an existing key against anything — the same
restraint that keeps it from re-enabling a realm an operator disabled.

### `Rotate`

```go
func (s *KeyService) Rotate(ctx context.Context, realmID uuid.UUID, alg key.Algorithm) (*key.Key, error)
```

Prepares outside, then inside one transaction: find the active key, `Deactivate`
it, `Update`, and `Create` the new one. Two concurrent rotations collide on
`uq_realm_keys_active` and one loses, which is the correct outcome rather than
two active keys.

Rotating a realm that has no active key for that algorithm is not an error — it
creates one. That is what makes rotation the recovery path after a key was
disabled by mistake.

### The signer port

Named `SignerSource`, not `Signer`, because it is declared in a file that also
returns `crypto.Signer` and two `Signer`s in one file is a reading tax for no
gain. It also matches the house naming: `CertificateSource` is the same idea —
an interface named for what it produces.

```go
type SignerSource interface {
    SignerFor(ctx context.Context, realmID uuid.UUID, alg key.Algorithm) (crypto.Signer, key.Ref, error)
}
```

`key.Ref` is the `kid`/`alg` pair a JWS header carries. `*KeyService` satisfies
the interface: it finds the active row, calls `Sealer.Open` with the AAD it
reconstructs from `realm_id ‖ kid`, parses the PKCS#8, and returns.

**Nothing in this slice consumes it.** It exists so slice 4 depends on an
interface rather than on the struct, and it is one method.

### Where a KMS enters

This was the reason for the shape, so it is worth stating precisely: a KMS
replaces the whole `SignerSource` implementation, not a part inside it. A KMS never
returns private key material, so "open the seal and parse" has no analogue
there. What does have an analogue is "give me something that can sign for this
realm" — which is exactly the interface boundary. `crypto.Signer` is itself the
standard library's "I sign without handing you the key", and a KMS or HSM client
implements it without the caller knowing.

Same pattern as `CertificateSource`: what changes is on the far side of the
interface, and no caller is edited.

### The port hands back a `crypto.Signer`, and slice 4 inherits a trap

Named here because this slice chose the shape, and neither is this slice's problem to solve:

- `rsa.PrivateKey.Sign(rand, digest, crypto.SHA256)` produces a PKCS#1 v1.5
  signature, which is what RS256 wants. PS256 would need `*rsa.PSSOptions` and
  is a different `alg`.
- `ecdsa.PrivateKey.Sign` produces **ASN.1 DER**, and JWS ES256 requires the
  fixed-width `R ‖ S` concatenation — 64 bytes for P-256, each half
  left-padded. Whoever assembles the JWS has to convert. A DER signature in a
  JWS is accepted by nothing.

### No cache, deliberately

Opening a seal and parsing a key is cheap; the cost is the database round trip,
and nothing in this slice signs per request. A cache here would be an
optimisation with no measurement behind it, and it would bring its own problem:
replica A rotates through the CLI and replica B keeps signing with the key it
cached. That is a problem to solve when there is a consumer to measure, in slice
4, and a short TTL is the likely answer.

The JWKS endpoint reads the database per request. It is a single indexed lookup
on `(realm_id, status)` returning a handful of rows, bounded by the request
timeout middleware, and answered with cache headers that keep well-behaved
clients off it. If that turns out to be wrong it will be wrong with numbers
attached.

## The HTTP surface

### The route

```
GET  /realms/{slug}/protocol/openid-connect/certs
HEAD /realms/{slug}/protocol/openid-connect/certs
```

Identical to Keycloak. No specification requires any particular path — clients
arrive through `jwks_uri` in discovery — so compatibility with the product
customers are migrating from is the only argument available, and it is the one
taken. `certs` is a misnomer inherited along with it: what is served is public
keys, not certificates.

`HEAD` is registered explicitly because chi routes by method, and the
alternative is a 405 for a method the endpoint plainly supports. The page
surface already does this for the same reason.

### `/realms` is mounted, not registered inline

The handler is built in `setWeb`, beside `app.page`, and held as `app.oidc`. It
needs `app.realms` and `app.keys`, which `setServices` has already produced by
then — the step list is the ordering guarantee. `setRouter` mounts it:

```go
app.surfaces.Mount("/realms", app.oidc.Routes())
```

`app.surfaces` is the group `setRouter` itself assigns, so the mount happens in
the same step, after the group closure returns. chi allows that: a group's
middleware is fixed inside the closure, and routes registered on the captured
router afterwards go through it.

The comment already in `router.go` explains why this matters: on an inline group
chi assigns `NotFound` and `MethodNotAllowed` to the parent mux, so a group
cannot scope its own. Only `chi.Mount` builds a mux that carries handlers of its
own.

Without the mount, a wrong path under `/realms/...` answers the page surface's
HTML 404. An HTML document is the wrong answer to a protocol endpoint. The
branch is created now, with its own 404 and 405 in the OAuth 2 error format
`internal/http/response` already writes, and every endpoint slices 4 and beyond
add lands inside it.

### Resolving the realm, and the status rule

The handler does not query by slug itself, and it does not check status either.
`RealmService` gains

```go
// Resolve is the single door every protocol endpoint uses to turn a slug into
// a realm. It applies the status rule, so no endpoint has to remember it.
func (s *RealmService) Resolve(ctx context.Context, slug string) (*realm.Realm, error)
```

`FindBySlug` keeps the tolerance it has today — it returns archived realms,
because creation has to see them or a burned slug gets handed out again. Those
are opposite tolerances for opposite callers, which is why they are two methods
and not one with a flag. `Resolve` returns `realm.ErrNotAvailable` for an
archived realm and `realm.ErrNotFound` for an unknown slug, and the handler
answers `404` to both without distinguishing them: telling a caller which realms
exist but are archived is information the endpoint has no reason to publish.

- `archived` → 404. The row exists to keep its slug and issuer occupied so that
  cached discovery and dead tokens cannot follow them to a new realm. It does
  not exist to serve anything.
- `disabled` → **serves the JWKS normally**. This is counterintuitive and was
  decided in slice 1 with the reason attached: stopping the JWKS revokes
  nothing, it only makes "realm disabled" indistinguishable from "key rotated"
  for a client holding a token that is still inside its lifetime.
- unknown slug → 404, in the same JSON shape.

The body is the OAuth 2 error object `internal/http/response` already writes,
with `error: "invalid_request"` — the closest of the eight codes in RFC 6749
section 5.2, since none of them describes a missing resource and inventing a
ninth would put a non-standard code in the field clients switch on. The
description names the realm slug, which the caller supplied and already knows.

### The document

```json
{"keys": [ { "kty": "...", "kid": "...", "alg": "...", "use": "sig", ... } ]}
```

Keys with status `active` or `passive`, never `disabled` — leaving the document
is the definition of `disabled`.

**Ordered by `id` descending, not by `created_at`.** Deterministic ordering is
required rather than cosmetic, because the ETag is computed over the rendered
bytes, and `created_at` does not provide it: on SQLite a timestamp is `TEXT`
written as RFC 3339 with trailing zeros trimmed, so `…:00Z` and `…:00.5Z` sort
by comparing `Z` against `.` and the row with no fractional part sorts *after*
the one that has it. Ordering by `id` avoids the trap and costs nothing: a
UUIDv7 in canonical form is fixed-width hexadecimal with the timestamp in the
leading bits, so lexicographic order is chronological order — on the three
dialects that store it as text, and on Postgres, which compares `uuid` by byte
value.

Newest first, which in practice puts the active key first, since rotation
creates the newest row.

A realm whose keys are all disabled answers `200` with `{"keys":[]}`, not `404`.
The realm exists; it has nothing to publish.

### Content type

`application/jwk-set+json`, the media type RFC 7517 registers. Keycloak answers
`application/json`. Every client library parses the body without inspecting the
type, so the registered one is used even though the route above chose
compatibility.

This does not fit `response.WriteJSON`, for two reasons: it sets
`application/json;charset=UTF-8` with `Set`, overwriting anything a handler put
there, and it marshals internally, so the handler never sees the bytes the ETag
has to hash. `internal/http/response` therefore gains

```go
func WriteBytes(w http.ResponseWriter, status int, contentType string, body []byte)
```

and `WriteJSON` becomes a call into it with the default content type. The change
is small and the package already anticipated it — the comment on `WriteJSON`
says discovery and JWKS are meant to be cached, which is why it sets no
`Cache-Control` of its own.

### Caching

`Cache-Control: public, max-age=300`, an `ETag` over the rendered document, and
`304` on a matching `If-None-Match`.

An OIDC client fetches the JWKS on start, on schedule, and in a burst whenever
it meets an unknown `kid` — which is exactly what happens to every client at
once after a rotation. Without cache headers each of those is a query.

Nothing here is secret, so `public` is correct: the whole document is public
keys.

## The CLI

`internal/cli` gains `key`, dispatched beside `migrate` and opening the database
through the same configuration translation the server uses, so a maintenance
command never runs under different TLS or pool settings than the process that
serves traffic.

```
aegisd key list <realm>
aegisd key rotate <realm> <algorithm>
aegisd key disable <realm> <kid>
aegisd key enable <realm> <kid>
aegisd key rewrap
```

The realm is addressed by **slug**, not UUID — a human types this.

**The algorithm is positional, not a flag.** Everything after the subcommand is
handed to the configuration builder's flag parser, where an unknown flag is an
error, so `--alg` would have to be taught to a parser that has nothing to do
with keys.

`enable` is there because `disable` without it makes a mistyped `kid` a problem
only SQL can fix — which is the situation the CLI exists to prevent. An unknown
slug exits 1 on every verb.

The algorithm is **required** on `rotate` and takes one value. Rotating both
algorithms is two rotations, and an operator rotating a realm's entire signing
surface should have to say so twice. Omitting it is a usage error, not a
default, and it is refused during dispatch — before the configuration builder
runs and before any database is opened.

Every verb is argument parsing, one call into `KeyService`, and output
formatting. No SQL, no transaction of its own, no rule that exists only here.
That is the constraint that makes slice 5's admin API call the same methods
instead of growing a second implementation that diverges at the first bug fixed
on one side.

`rewrap` is likely to stay CLI-only permanently, and not because of ordering:
it needs both master keys in one process, and doing it over HTTP means putting a
master key in a request body.

### Exit codes

`0` on success, `1` on failure, following `fail(err)` in `migrate.go`. `migrate
status` has meaningful codes because it is a deployment gate; nothing here is,
so nothing here needs them.

`key disable` on an active key exits 1 with the message naming the rotation that
has to happen first.

## Boot

The step list becomes:

```
setLogger, setGraceful, setHealth, setDatabase, setSchema,
setCrypto, setServices, setCertificates, setWeb, setRouter, setHttpServer
```

### `setCrypto`

Builds the `Sealer` from the `crypto` section. It is a step of its own because
it reaches outside the process — a `_FILE` secret is read here — and because it
has to exist before `setServices`, which seeds keys. It is where "production
without a master key does not boot" becomes true.

### `setServices`

Builds the store, then `KeyService`, then `RealmService` with the key service in
hand, then seeds. `app.keys` is held on the `Application` for the reason already
written in the comment above `setServices` about `app.realms`: built as a local,
the admin API would later construct a second one that is not the application's.

### The seed's time budget changes meaning

The seed context borrows `Database.ConnectTimeout` — 10 s by default — and the
comment there explains the borrow as "a few single-row round trips on an open
connection". That stops being the whole truth: on a first boot the budget now
also covers two key generations. Two pairs, RSA-2048 and P-256, fit
comfortably, but the comment has to say so, or the next person tuning
`connect_timeout` down will not know what they are cutting.

### Logging

`master realm ready` gains the active `kid`s. It is the first thing anyone looks
for when a client reports a signature it cannot verify.

### No new readiness check

The sealer reaches nothing external after boot. A check here would report on
memory. Health stays as it is.

## Concurrency

Three races, and what resolves each:

- **Two replicas seeding the master realm's keys.** Both generate, both insert,
  `uq_realm_keys_active` rejects one, the loser re-reads. Same shape as the
  realm seed's, which already tolerates `ErrSlugTaken`.
- **Two rotations at once**, from two operators or a retried command. Same index,
  same outcome: one wins, one is told the active key already exists.
- **A rewrap running while the server serves.** The sealer holds both keys and
  opens by `kek_id`, so a row mid-rewrap is readable by every replica regardless
  of which key sealed it.

## Operational consequences

- **Production gains a required secret.** A deployment that boots today stops
  booting after this slice until `AEGIS_CRYPTO_MASTER_KEY` is set. That belongs in the
  release notes and in `docs/deployment.md`, not only in a validation message.
- **Backups now contain material that is useless without the master key.**
  Restoring the database alone does not restore a working aegis. The master key
  has to be backed up separately and, being a secret, not beside the dump.
- **First boot is slower.** Two key generations per realm created, once.
- **Every subcommand now requires the master key in production, `migrate`
  included.** Configuration is built and validated before `Dispatch` chooses a
  runner, so `aegisd migrate status` used as a deployment gate — an init
  container, a pipeline step — starts failing until the secret is mounted there
  too. It does not need it to do its work; it needs it because the process it
  runs in refuses to be misconfigured. Naming it here is cheaper than the
  operator discovering it when the gate fails.
- **`aegisd key rewrap` is the only supported way to change the master key.**
  Changing the variable without rewrapping leaves every row sealed under a
  `kek_id` the process no longer holds, and every realm unable to sign.

## Testing

### Unit

- **Thumbprint against RFC 7638 §3.1.** The RFC prints a worked JWK and its
  thumbprint; both are pasted into the test verbatim from the RFC text rather
  than produced by this implementation. It is the one check in the suite that is
  genuinely independent.
- **JWK encoding.** RSA `n` with no leading zero byte; EC `x` and `y` padded to
  32 bytes, including a generated key whose coordinate legitimately starts with
  a zero byte — otherwise the padding path is never exercised.
- **Transitions.** Every allowed one, and every rejected one, including the
  refusal to disable an active key.
- **`Sealer`.** Round trip; wrong AAD fails; unknown `kek_id` fails; a single
  flipped byte in the ciphertext fails. The three are one guarantee seen from
  three sides, and GCM is what provides it.
- **Configuration.** Both forms of a variable set is an error; a non-base64
  value is an error; a value that decodes to 31 or 33 bytes is an error;
  production with the development constant is an error; development with nothing
  set warns and proceeds.
- **Services**, against a fake store and a fake generator, so no test pays for
  real RSA generation except the ones that are about RSA.

### The test that closes the slice

Sign a payload with the `crypto.Signer` the port returned, then verify that
signature with a public key **rebuilt from the JSON the JWKS endpoint served**.

If it passes, `kid` → published key → key that signed is proven end to end,
which is the only thing an OIDC client ever does. Both algorithms.

### Integration, tagged, on all four engines

- **`uq_realm_keys_active` rejects a second active key** for the same
  `(realm, purpose, algorithm)` — on Postgres, MySQL, MariaDB and SQLite. This
  one is not optional. The portability of NULLs in a unique index is the premise
  the whole schema rests on, and slice 1 is where this project learned what an
  unverified four-engine premise costs.
- The same index **permits** many passive rows for one `(realm, algorithm)`,
  which is the other half of the trick working.
- `ck_realm_keys_marker` rejects an active row with a NULL marker and a passive
  row with a marker.
- Constraint-name translation produces the right domain error on each engine,
  SQLite's column-naming spelling included.
- `ON DELETE CASCADE` removes a realm's keys. Nothing deletes realms today; the
  constraint is still declared, so it is still tested.
- The two migration invariants — one statement per file, identical version sets
  across dialects — already exist and cover the new files with nothing to write.

### Boot, in `test/integration`, against the compiled binary

- Boots; the master realm has two active keys; the JWKS serves two.
- Restarts; still two, same `kid`s. The seed is idempotent.
- `aegisd key rotate master RS256`; the JWKS serves three, with a new
  active `kid` and the old one still published.
- `aegisd key disable` on the passive key; the JWKS serves two again.
- `aegisd key disable` on the active key; exit 1, JWKS unchanged.
- Production without `AEGIS_CRYPTO_MASTER_KEY` does not boot.
- Every existing test in `test/integration` that boots under the production
  profile needs the variable added. They pass today because the profile
  required no secret; after this slice they fail for a reason that has nothing
  to do with what they assert, which is the kind of failure that gets a test
  deleted instead of fixed.
- Production with the development constant does not boot.
- A rewrap interrupted partway and resumed ends with every row at the new
  `kek_id`, and the JWKS is served correctly at every point in between.
- `archived` realm answers 404; `disabled` realm answers its JWKS.
- A wrong path under `/realms/...` answers JSON, not HTML.

## Open, and deliberately not resolved here

- **Where `SignerSource` finally lives.** It is declared in `internal/service` now,
  satisfied by a struct in the same package, which is the consumer-declares rule
  applied for a consumer that does not exist yet. Slice 4 may move it next to
  the token service. One interface, one method; moving it is not expensive.
- **RSA key size is fixed at 2048.** Configurable sizes need somewhere to
  configure them.
- **Signer caching and its invalidation across replicas.** Slice 4, with
  measurements.
- **Whether a disabled realm should keep serving its JWKS forever.** The
  decision holds for as long as a token issued before the realm was disabled can
  still be alive. There is no eviction today because there is no token TTL
  today; TTLs land in slice 4.
- **Key import.** An admin API operation with its own validation surface, and
  the reason the `private_key` column's ceiling is written down.
