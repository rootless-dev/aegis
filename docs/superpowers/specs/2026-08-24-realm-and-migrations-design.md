# Phase 1, slice 1: migrations on boot, the realms table, and the master realm

Status: design approved in conversation, not yet implemented
Branch: `feat/realm-and-migrations`

## What this slice is

The database layer landed in `0.0.3` with a migration runner that has no caller
in production, on purpose. The page surface landed in `0.0.4`. Neither of them
creates a table. This slice is the first one that writes business state: it
wires the runner into the boot, owns the SQL, creates `realms`, and seeds the
master realm.

It ends with a running aegis that has a schema, one realm in it, and a
`aegisd migrate` subcommand — and with no HTTP surface for any of that. Routes
for realms belong to the admin API, which is slice 6.

## What this slice is not

Named because each was deliberately left out, not forgotten:

- No HTTP routes, handlers, or console screens for realms.
- No realm signing keys, no JWKS, no discovery document. That is slice 2, and
  it is what will first exercise the `issuer` column this slice stores.
- No identities, credentials, or sessions. Slices 3 and 4.
- No admin bootstrap from environment credentials. Slice 5. This slice creates
  the master realm row and nothing inside it.
- No `aegisd realm reissue`. The domain-migration path is named here because
  `Reissue` has to exist on the repository for the development seed, but the
  subcommand that would call it in production is not built.
- No down migrations, ever. See "Only up".
- No custom domains per realm. The `issuer` column is what has to accommodate
  them later; nothing else does.

## Decisions this slice implements

Every one of these was closed in conversation before any file was written.
They are recorded here because the reasoning does not survive in the code, and
because none of them can be reversed after the first on-prem installation.

| Area | Decision |
|---|---|
| Migration source | `internal/migrations` owns the `embed.FS`; one directory per dialect, MariaDB separate from day one |
| Direction | Only `.up.sql`. No down migrations |
| File names | Sequential — `0001_create_realms.up.sql` |
| Control table | `aegis_schema_migrations`, not golang-migrate's default |
| Boot | Migration runs inside `application.New`, before anything reads a table |
| Toggle | `database.migrate.on_boot`, default `true` |
| Version check | Always runs. Refuses a schema behind the binary, tolerates one ahead |
| CLI | `cmd/aegisd` with `migrate`, `migrate status`, `migrate force` |
| Identifiers | UUIDv7, rendered as text; `uuid` native on Postgres only |
| Timestamps | Generated by the application in UTC, microsecond precision |
| Soft delete | None, anywhere. `realms` archives by status, which is not the same thing |
| Constraints | Every index and constraint explicitly named |
| Domain shape | Two types — a pure-Go aggregate and a GORM record — with private fields and accessors |
| Transactions | Unit of work, explicit, spanning repositories |

## Package layout

```
internal/
  migrations/            embed.FS owner, one directory per dialect
    postgres/  mysql/  mariadb/  sqlite/
  domain/
    realm/               the aggregate; no imports outside the standard library
  repository/            GORM records, mappers, the unit of work
  service/               use cases, and the repository interfaces they consume
  cli/                   subcommand dispatch and the commands themselves
cmd/
  aegisd/                main, thin
```

Four packages are new and one moves. `internal/handler` already holds `page`
from the previous slice and gains nothing here: realms get no HTTP surface
until slice 6.

`cmd/server` is renamed to `cmd/aegisd`. The binary has been called `aegisd`
in every build file since the beginning; only the package directory disagreed,
and it stops being defensible once the binary does more than serve.

### Why the dispatch is not in `cmd/`

`sonar-project.properties` excludes `cmd/**` from coverage, with a stated
reason: the entry point is assembly with no branching of its own. Subcommand
dispatch is branching. It lives in `internal/cli`, which stays measured;
`cmd/aegisd/main.go` keeps its current shape and calls into it.

## The migration subsystem

### `internal/migrations`

Two exported symbols and nothing else:

```go
// For returns one dialect's migrations, rooted at its directory so the runner
// sees files rather than directories.
func For(driver string) (fs.FS, error)

// Latest reports the highest version a dialect carries. Derived rather than
// declared, because a constant is one more thing to forget to bump.
func Latest(driver string) (uint, error)
```

`For` is `fs.Sub` over the embedded tree. `Latest` parses the numeric prefix of
each `*.up.sql` entry and returns the maximum, refusing a directory with no
migrations rather than reporting zero — zero is a real version meaning "empty
database", and the two must not be confused.

### One statement per file, and it is not a style rule

`internal/infra/database/mysql.go:72` sets `cfg.MultiStatements = false`, and
the migration connection is built from the same DSN builder as the pool. A
migration file with two statements fails on MySQL and MariaDB while passing on
Postgres and SQLite — green on three engines, red on the two that matter most
to an on-prem customer.

Every file holds exactly one statement.

That has a consequence the parity test makes non-negotiable: **the four
directories always hold the same version numbers.** A dialect cannot get an
extra numbered file the others do not have, because the parity test is exactly
what forbids it — and that test is the thing standing between us and a customer
on MariaDB discovering a missing column months later.

So a migration that needs more than one statement is split the same way in all
four dialects, and every statement gets a version number every dialect uses.
The case that would otherwise force divergence is the FK index: Postgres does
not create one for a foreign key and InnoDB does. Declaring it explicitly in
all four — which is already the decision from the design conversation — makes
the redundant declaration on MySQL and MariaDB harmless and keeps the numbering
identical.

For `0001` the question does not arise: all four dialects express the primary
key, both unique constraints and the check inside a single `CREATE TABLE`.

### Only up

There are no `.down.sql` files. A down migration that drops a column is data
loss wearing the costume of a rollback, and on-prem the real recovery path is
the customer's backup. `requireUpMigrations` in the existing runner already
tolerates their absence, and `Down()` is never called.

### The control table

`db.migrator()` currently passes an empty `Config{}` to all three
golang-migrate database drivers, which leaves the control table at the library
default: `schema_migrations`.

That name is shared with Rails, with every other golang-migrate project, and
with a good part of the ecosystem. In a customer database that aegis shares
with another application, the failure is not an error — it is silence. If the
neighbour also uses golang-migrate, aegis reads *their* version, concludes it
is at 47, applies nothing, and boots clean with no table of its own.

The table becomes `aegis_schema_migrations`, set through each driver's config:

- `pgmigrate.Config{MigrationsTable: ...}`
- `mysqlmigrate.Config{MigrationsTable: ...}`
- `sqlitemigrate.Config{MigrationsTable: ...}`

This has to be right before the first installation. Changing the name later
means migrating the migration table, which is the one place in the system where
a manual step has no net.

### Version check

A new exported function on `*DB`, next to the existing `SchemaVersion`:

```go
// VerifySchema compares the recorded version against what the caller carries.
// A schema ahead is tolerated: during a rolling update the previous binary runs
// beside the new one, and refusing an unrecognised version would remove the
// ability to roll back.
//
// The context is accepted and unused, matching SchemaVersion — golang-migrate's
// version read takes none.
func (db *DB) VerifySchema(_ context.Context, expected uint) error
```

The rules, in order:

1. Dirty flag set → refuse, with the existing `SchemaDirtyError`.
2. Recorded version below `expected` → refuse, naming both versions and the
   subcommand that fixes it.
3. Recorded version above `expected` → log at warn and continue.
4. Equal → nothing.

Rule 3 is the one that is not obvious, and it exists for rollback. During a
rolling update the old binary and the new one run side by side; the new one has
already migrated. If the old one refuses to start on a version it does not
recognise, rollback becomes impossible at exactly the moment it is needed.

The check runs on every boot, not only when `on_boot` is false. With migration
enabled it is nearly tautological and costs one `SELECT`, and it still catches
the case where `Up()` returned `ErrNoChange` against a database that is ahead.

### Configuration

A subsection of `database`, because it configures that database's schema:

```yaml
database:
  migrate:
    on_boot: true
    timeout: 5m
    lock_timeout: 0s
```

| Key | Env | Flag | Default | Validation |
|---|---|---|---|---|
| `on_boot` | `DATABASE_MIGRATE_ON_BOOT` | `--migrate-on-boot` | `true` | none — a bool cannot be wrong |
| `timeout` | `DATABASE_MIGRATE_TIMEOUT` | — | `5m` | must be positive; the runner already refuses zero |
| `lock_timeout` | `DATABASE_MIGRATE_LOCK_TIMEOUT` | — | `0s` | must not be negative; zero leaves golang-migrate's own default |

`Migrate` is a `*Migrate` pointer field on `configs.Database`, following the
`Pool` precedent, and `defaultDatabase()` populates it. `Database.Validate`
reports a missing section rather than dereferencing nil, matching how
`Application.sections()` treats every other block.

The flag follows the `--dev` pattern in `flag_source.go` exactly: a `*bool` in
the `flags` struct so an absent flag never overwrites what the file or the
environment set.

`configbuilder` gains `applyDatabaseMigrate`, called from `applyDatabase`, in
the shape `applyDatabasePool` already has.

### Boot order

`New`'s step list gains two entries:

```go
instance.setLogger,
instance.setGraceful,
instance.setHealth,
instance.setDatabase,
instance.setSchema,     // new
instance.setServices,   // new
instance.setCertificates,
instance.setWeb,
instance.setRouter,
instance.setHttpServer,
```

`setSchema` migrates when `on_boot` is true, then verifies in every case. It
builds its own context from `migrate.timeout`, because `New` takes none and
`main` constructs none.

`setServices` constructs the store and the realm service onto the
`Application`, then runs the master realm seed. Two steps rather than one
because they have different jobs, and because the seed needs a service that
something has to own: if it were built as a local inside `setSchema`, slice 6
would construct a second one for its handlers and neither would be the
application's.

`Application` gains two fields:

```go
store  service.Store
realms *service.RealmService
```

Neither is a `Resource`: they hold no goroutine and no socket, and the pool
underneath them is already taken down by the `graceful.Register("database",
...)` that `Run` performs before it registers anything else. Nothing is added
to `resources()`.

### `application.New` gains no `context.Context`

Adding one would change a public signature for a single caller that can build
its own. `setSchema` uses `context.WithTimeout(context.Background(), ...)`.
This is a deliberate narrowing, and the moment a second step needs a
caller-supplied deadline, the signature should change rather than grow a second
private context.

`application.New` has two callers: `main`, and `internal/application/database_test.go`.
`newTestApplication` in `router_test.go` builds the struct by hand and calls
`setWeb` and `setRouter` directly, so the router suite is untouched by the two
new steps.

### The unit suite starts migrating

`internal/application/database_test.go` carries no build tag. It calls
`application.New` with a development configuration whose SQLite file lives in
`t.TempDir()` — which means that from this slice on, `make test` runs real
migrations and seeds a master realm on every run, against the engine compiled
into the binary.

That is acceptable and even useful: it is free coverage of the whole boot path
with no container. It is written down because it is a change in what the unit
suite does, and because the two tests there should assert it deliberately
rather than exercise it by accident — after `New`, the schema is at `Latest`
and a realm with slug `master` exists.

`TestNewFailsWhenTheDatabaseIsUnreachable` is unaffected: its path points into
a directory that does not exist, so `Open` fails before `setSchema` is
reached.

## The schema

### `0001_create_realms`

Seven columns, and the reasoning for each closed in conversation.

Postgres — `internal/migrations/postgres/0001_create_realms.up.sql`:

```sql
CREATE TABLE realms (
    id           uuid           NOT NULL,
    slug         varchar(63)    NOT NULL,
    display_name varchar(255)   NOT NULL,
    issuer       varchar(255)   NOT NULL,
    status       varchar(16)    NOT NULL,
    created_at   timestamptz(6) NOT NULL,
    updated_at   timestamptz(6) NOT NULL,
    CONSTRAINT pk_realms PRIMARY KEY (id),
    CONSTRAINT uq_realms_slug UNIQUE (slug),
    CONSTRAINT uq_realms_issuer UNIQUE (issuer),
    CONSTRAINT ck_realms_status CHECK (status IN ('active', 'disabled', 'archived'))
);
```

MySQL and MariaDB — byte for byte identical to each other, in two directories:

```sql
CREATE TABLE realms (
    id           CHAR(36)     NOT NULL,
    slug         VARCHAR(63)  NOT NULL,
    display_name VARCHAR(255) NOT NULL,
    issuer       VARCHAR(255) NOT NULL,
    status       VARCHAR(16)  NOT NULL,
    created_at   DATETIME(6)  NOT NULL,
    updated_at   DATETIME(6)  NOT NULL,
    CONSTRAINT pk_realms PRIMARY KEY (id),
    CONSTRAINT uq_realms_slug UNIQUE (slug),
    CONSTRAINT uq_realms_issuer UNIQUE (issuer),
    CONSTRAINT ck_realms_status CHECK (status IN ('active', 'disabled', 'archived'))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_bin ROW_FORMAT=DYNAMIC;
```

SQLite:

```sql
CREATE TABLE realms (
    id           TEXT NOT NULL,
    slug         TEXT NOT NULL,
    display_name TEXT NOT NULL,
    issuer       TEXT NOT NULL,
    status       TEXT NOT NULL,
    created_at   TEXT NOT NULL,
    updated_at   TEXT NOT NULL,
    CONSTRAINT pk_realms PRIMARY KEY (id),
    CONSTRAINT uq_realms_slug UNIQUE (slug),
    CONSTRAINT uq_realms_issuer UNIQUE (issuer),
    CONSTRAINT ck_realms_status CHECK (status IN ('active', 'disabled', 'archived'))
) STRICT;
```

Notes that are not obvious from reading the DDL:

**`varchar(255)` on `issuer` is forced by the unique index, not by taste.**
InnoDB caps an index key at 3072 bytes and `utf8mb4` counts four bytes per
character. The conventional `varchar(2048)` for a URL would be 8192 bytes and
the MySQL migration would fail at `CREATE`. 255 characters is 1020 bytes, and
an issuer longer than that is pathological.

**`STRICT` needs SQLite 3.37, and that is ours to guarantee.** The engine is
compiled into the binary — `ncruces/go-sqlite3` currently reports 3.53.0 — so
unlike the other three, the operator does not choose the version. The "SQLite
3.35+" floor recorded in the conversation is informational; nothing enforces it
because nothing can contradict it.

**`ROW_FORMAT=DYNAMIC` is stated rather than assumed.** It is the default on
MySQL 8 and MariaDB 10.6, but it is what keeps the 3072-byte key limit rather
than the 767-byte one of the older formats, and a customer with a non-default
`innodb_default_row_format` would otherwise fail at `CREATE` with an error that
does not mention row format.

**No index on `status`.** `realms` holds tens of rows; an index there would
cost writes and buy nothing measurable.

### Slug rules

`^[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$` — lowercase alphanumerics and hyphens,
one to 63 characters, no leading or trailing hyphen.

63 is the DNS label limit. If per-realm custom domains ever ship, the slug
already fits as a subdomain. The absence of `.` in the character class is what
makes a realm named `.well-known` unrepresentable, which is cheaper than a
reserved word for it.

Reserved slugs: `master`, `admin`, `api`, `aegis`. `master` because the seed
owns it; the rest defensively, for routes that do not exist yet.

**The reservation is a service rule, not a domain one**, and the difference is
load-bearing: the seed creates a realm whose slug is `master`, so a constructor
that refused reserved slugs would refuse the one realm the system cannot start
without.

So the split is:

- `realm.New` validates **form** — the regular expression and the length. A
  realm named `master` is perfectly well formed.
- `RealmService.Create` additionally refuses a **reserved** slug. That is
  policy about who may claim a name, which is a use-case concern and not a
  property of the aggregate.
- The seed does not go through `Create`. It has its own path in
  `RealmService`, which is also what keeps `ErrSlugReserved` from being a lie.

`ErrSlugReserved` still lives in the `realm` package, because the vocabulary
belongs with the aggregate even when the rule that raises it does not.

The database enforces length and uniqueness and nothing else — a `CHECK` with a
regular expression is one more thing that differs across four dialects.

### Status

`active`, `disabled`, `archived`, enumerated in a named `CHECK` in all four
dialects and in a Go type in the domain. No native `ENUM`, no lookup table.

The list starts closed and short. `pending` is absent because realm creation is
atomic — the unit of work below is what makes that true, and what keeps the
state unrepresentable. `suspended` is absent because it differs from `disabled`
only in who may reverse it, and that distinction needs an authorization model
that does not exist until slice 5.

What `disabled` means, in behaviour, was settled in conversation and is
recorded here because nothing in this slice implements it yet: refuse new
authentication and token issuance including refresh; keep serving JWKS and
discovery, since withholding them revokes nothing and only makes validation
fail indistinguishably from a key rotation; invalidate live sessions; let
already-issued access tokens live out their TTL; keep the realm's own
administrative API reachable, or nobody can re-enable it.

`archived` behaves as `disabled` plus invisibility in listings, and its row is
never deleted. That is the opposite of the reasoning that banned soft delete
elsewhere: a deleted realm's slug and issuer must stay occupied, because
reusing them would point cached discovery documents and live tokens from a dead
realm at a new one.

## The domain

`internal/domain/realm` imports nothing outside the standard library and
`github.com/google/uuid`.

```go
type Realm struct {
    id          uuid.UUID
    slug        string
    displayName string
    issuer      string
    status      Status
    createdAt   time.Time
    updatedAt   time.Time
}
```

Private fields with accessors. This is what makes the issuer immutable in a way
the compiler enforces rather than a way people remember.

### Two doors, and only two

```go
// New generates the identifier, derives the issuer, and stamps both timestamps
// to the same UTC instant.
func New(slug, displayName string, publicBaseURL *url.URL) (*Realm, error)

// Rehydrate is the repository's door back in. It takes the stored issuer as
// given: deriving here would recompute every realm's identity from whatever
// public url this process holds, which is what the stored column prevents.
func Rehydrate(id uuid.UUID, slug, displayName, issuer string, status Status, createdAt, updatedAt time.Time) (*Realm, error)
```

The split is forced by the issuer decision, not by taste. `New` builds
`{public_base_url}/realms/{slug}`; if `Rehydrate` shared that path, every
`SELECT` would recompute the issuer from whatever `public_url` the process
currently holds — which is precisely the silent drift the stored column was
chosen to make impossible.

`New` generates the identifier with `uuid.NewV7()`, which returns an error —
it reads the system clock and the entropy source, and both can fail. That error
is wrapped rather than discarded; a `uuid.Must` here would turn a transient
failure into a panic inside a request.

`Rehydrate` still validates. Data read from a customer database that a DBA has
touched is not trusted input. That includes the status column: the record holds
a `string`, so the mapper goes through `realm.ParseStatus`, which returns
`ErrStatusInvalid` for anything outside the three values. The `CHECK`
constraint should make that unreachable — on an engine that honours it, which
is why the MySQL floor moves below.

### Mutation

`Rename(displayName string) error` and `SetStatus(s Status) error` on the
aggregate, both stamping `updatedAt`. There is no setter for `id`, `slug`,
`issuer`, or `createdAt`.

Reissuing is not a method on the aggregate. It is a repository operation
(below), because it is a deliberate administrative act and not part of the
realm's own behaviour.

### Errors

```go
// ErrSlugReserved is raised by the service, not here: the seed creates a realm
// whose slug is reserved and the aggregate has to allow it.
var (
    ErrNotFound           = errors.New("realm: not found")
    ErrSlugInvalid        = errors.New("realm: slug is not well formed")
    ErrSlugReserved       = errors.New("realm: slug is reserved")
    ErrSlugTaken          = errors.New("realm: slug is already in use")
    ErrIssuerInvalid      = errors.New("realm: issuer is not well formed")
    ErrIssuerTaken        = errors.New("realm: issuer is already in use")
    ErrDisplayNameInvalid = errors.New("realm: display name is empty")
    ErrStatusInvalid      = errors.New("realm: status is not one of active, disabled, archived")
    ErrIDInvalid          = errors.New("realm: identifier is empty")
)
```

`gorm.ErrRecordNotFound` never crosses out of `internal/repository`. If it did,
`service` would import GORM to compare an error and the dependency direction
would invert. The repository translates; this is the pattern the other six
aggregates copy.

`ErrSlugTaken` and `ErrIssuerTaken` are translated from the driver's unique
violation, keyed off the constraint name — which is why every constraint in the
DDL above is named explicitly. Each dialect reports the violation differently,
and this is the one place in the slice where dialect-specific error handling is
unavoidable. It gets a table in `internal/repository`, and integration coverage
on all four engines.

## Persistence

`internal/repository`, flat. `realm.go` holds the repository; `realm_record.go`
holds the GORM struct and the two mapping functions. A sub-package per
aggregate would read `repository/realm.Repository`, which stutters.

```go
type realmRecord struct {
    ID          string    `gorm:"column:id;primaryKey"`
    Slug        string    `gorm:"column:slug"`
    DisplayName string    `gorm:"column:display_name"`
    Issuer      string    `gorm:"column:issuer"`
    Status      string    `gorm:"column:status"`
    CreatedAt   Timestamp `gorm:"column:created_at"`
    UpdatedAt   Timestamp `gorm:"column:updated_at"`
}

func (realmRecord) TableName() string { return "realms" }
```

The struct carries no `type:` tag on any field. GORM never generates DDL here —
`AutoMigrate` was rejected precisely because it does not version anything — so
a type tag would be a second, unenforced description of a column the migrations
already define, and the two would drift.

`toDomain` calls `realm.Rehydrate`; `fromDomain` reads the accessors. Roughly
forty lines per aggregate, six more times, and in exchange a column rename
never reaches the domain.

`Update` writes `display_name`, `status` and `updated_at` and no other column —
named in the statement rather than saving the whole record. The aggregate has
no setter that could change `slug` or `issuer`, so this is belt and braces; it
is here because the day someone adds one, the repository should not be the
thing that lets it through to the database.

The record stores the UUID as its canonical 36-character string on every
dialect. One Go mapping, four column types.

**Unverified, and it has to be settled by a test rather than by reasoning:**
whether GORM's Postgres driver, which is pgx underneath, accepts a Go `string`
bound to a `uuid` column without an explicit cast, on both insert and scan.

This is the same class of question as the timestamp one below, and that one
turned out to be a real defect — a driver deciding what Go type to hand back
from the declared column type. It is very likely to work here, and "very
likely" is not the standard for the mapping every other aggregate copies. The
integration case named below answers it. If a cast or a `uuid.UUID` field turns
out to be required, the fix is a `Scan`/`Value` pair local to
`realm_record.go`, exactly like `Timestamp`, and nothing else in this design
moves.

### Timestamps need a type of their own

A plain `time.Time` field does not survive a round trip on SQLite. Verified,
not reasoned about:

```
sql: Scan error on column "created_at": unsupported Scan,
storing driver.Value type string into type *time.Time
```

The write works — the driver formats the value as
`2026-08-25T12:34:56.123456Z`, `typeof()` reports `text`, and a `STRICT` table
accepts it. The read is what fails, because `ncruces/go-sqlite3` decides how to
hand a column back from the **declared column type**: a column declared `TEXT`
comes back as a Go `string`, and `database/sql` will not scan a string into a
`*time.Time`.

This would have surfaced on the engine that serves `make test` and the whole
development profile, and nowhere else.

Declaring the column `DATETIME` instead makes the driver convert, and it works
— but it costs `STRICT`, since `DATETIME` is not one of the types `STRICT`
accepts, and it leaves the round trip depending on one driver's reading of a
declared type name. Swap the SQLite driver one day and it breaks silently.

So `internal/repository` owns a small shared type instead:

```go
// Timestamp is what every record uses for a time column. A plain time.Time
// does not survive the round trip on SQLite: the driver hands a TEXT column
// back as a string, which database/sql will not scan into a *time.Time.
type Timestamp time.Time

// A time.Time rather than a formatted string: every driver already handles one,
// and formatting by hand would mean fighting each dialect's literal syntax.
func (t Timestamp) Value() (driver.Value, error) {
	return time.Time(t).UTC().Truncate(time.Microsecond), nil
}

// Tolerates what the drivers return: time.Time from Postgres and MySQL, text
// from SQLite.
func (t *Timestamp) Scan(src any) error
```

`Scan` accepts `time.Time`, `string` and `[]byte`, parsing the last two as
RFC 3339, and converts to UTC. Anything else is an error rather than a zero
value, so a column a DBA has filled with something unexpected fails loudly.

Both halves were exercised against a `STRICT` table with a `TEXT` column before
this was written: the value stores as text at microsecond precision and reads
back equal to what went in.

This is a no-op for Postgres and MySQL — `Value` hands them exactly what a
plain `time.Time` field hands them today — and a fix for SQLite. It is written
once and used by all seven aggregates, which is the reason it belongs in this
slice rather than being discovered in the next one.

### Unit of work

`Store` is declared in `internal/service`, next to the repository interface it
hands out, and `internal/repository` implements it:

```go
// service.Store is the transactional boundary. The repositories handed to the
// callback are bound to one transaction; the ones on Store itself are not.
type Store interface {
    Realms() RealmRepository
    InTx(ctx context.Context, fn func(Store) error) error
}
```

This means `internal/repository` imports `internal/service`, which looks like
it contradicts the note in `application/ports.go` about an implementation never
importing its own abstraction. It does not: that note is about `infra/certs`,
which sits *outside* the application layer, so importing it would point the
dependency outward. `repository` is an adapter and `service` is the use-case
layer, so this import points inward, which is the direction the rule asks for.

The alternative does not typecheck. A `Realms()` returning a concrete
`*repository.RealmRepository` does not satisfy an interface whose method
returns `service.RealmRepository` — Go requires the return types to match
exactly, not merely to be assignable. Declaring both interfaces in the consumer
is the only shape that composes.

The GORM implementation wraps `db.Transaction`, and the `Store` passed into the
callback carries the transaction's `*gorm.DB`. Nesting reuses the outer
transaction rather than opening a savepoint — one level is all this slice
needs, and a savepoint policy chosen before there is a caller for it is a guess.

This exists in slice 1 with one aggregate because slice 2 needs it with two.
Creating a realm will write the realm row and its signing key in one
transaction, and that atomicity is the entire argument for `pending` being an
unrepresentable state. Retrofitting a transaction story onto seven repositories
later is a signature change everywhere.

The alternative of carrying `*gorm.DB` in the `context` was rejected: nothing
in a signature would say a method participates in a transaction, and a
repository that forgot to read the context would write outside it with no
symptom until half of a write survived a rollback.

### `Reissue`

```go
// Separate from Update because the issuer is immutable by design. Two callers:
// the development seed, and the domain-migration command that does not exist
// yet.
func (r realmRepository) Reissue(ctx context.Context, id uuid.UUID, issuer string) error
```

Two callers, one of which does not exist yet: the development seed, and the
`aegisd realm reissue` of a real domain migration.

## The service

`internal/service` declares the interface it consumes — the consumer owns the
shape it depends on, the same reasoning `application/ports.go` already states
for `CertificateSource`.

```go
type RealmRepository interface {
    Create(ctx context.Context, r *realm.Realm) error
    FindByID(ctx context.Context, id uuid.UUID) (*realm.Realm, error)

    // Returns archived realms too: creation has to see them, or a burned slug
    // gets handed out again.
    FindBySlug(ctx context.Context, slug string) (*realm.Realm, error)
    List(ctx context.Context, q RealmQuery) ([]*realm.Realm, error)

    // Writes display_name, status and updated_at, and no other column.
    Update(ctx context.Context, r *realm.Realm) error

    // Separate from Update because the issuer is immutable by design.
    Reissue(ctx context.Context, id uuid.UUID, issuer string) error
}
```

`RealmService` exposes the full set: `Create`, `FindByID`, `FindBySlug`,
`List`, `Rename`, `SetStatus`, `Archive`.

There is no `Delete`. `Archive` is the D, and it moves the status. Nothing in
this system hard-deletes a realm; when a legal erasure requirement appears, it
becomes a separate administrative operation that also has to burn the slug and
the issuer, and that is a design conversation, not a method.

### `FindBySlug` has two callers with opposite tolerances

Creation must see archived realms — otherwise a burned slug is handed out again
and the failure the archive exists to prevent comes back through the side door.
Realm resolution for authentication must refuse them, alongside `disabled`.

So `FindBySlug` returns whatever is stored, archived included, and the status
check belongs to the single point that resolves a realm for a request. That
point does not exist in this slice; it arrives with the first authenticated
surface, and this paragraph is here so it is built once rather than remembered
in each handler.

### `List` paginates by keyset

```go
// RealmQuery is a keyset page over realms, ordered by id ascending.
type RealmQuery struct {
    // The zero UUID sorts before every UUIDv7, so an empty value needs no
    // special case in the query.
    After uuid.UUID

    Limit int

    // Empty means every status except archived.
    Status []realm.Status
}
```

Ordered by `id` ascending, which is chronological for free because UUIDv7
carries its creation time — the same property chosen against write
amplification pays again here.

`id > :after` has to mean the same thing on four engines, and it does, but not
by accident. Postgres compares `uuid` bytewise, and the canonical text form is
those bytes in hex order, so the two orderings agree. MySQL and MariaDB compare
under `utf8mb4_bin`, which the schema forces. SQLite's default `BINARY`
collation on `TEXT` does the same. Had any of the three been case-insensitive
or locale-aware, pagination would have skipped or repeated rows on that engine
alone.

The zero `uuid.UUID` sorts before every UUIDv7, so an empty `After` starting at
the beginning needs no special case in the query.

Offset pagination was rejected: it degrades with depth and it is unstable under
concurrent insertion, where a new row shifts every later page and readers skip
or repeat records. On `realms`, with tens of rows, none of that is observable;
this is the shape the other six aggregates copy, and `identities` will not be
tens of rows.

`Status` empty means "everything except archived". Listing tombstones by
default is not what any caller wants, and an explicit filter can still ask.

`Limit` is clamped: zero or negative becomes 50, and anything above 500
becomes 500. Clamping rather than rejecting, because a page size is not
something a caller should be able to get wrong enough to fail on.

## The master realm seed

Runs at the end of `setServices`, once the schema is migrated and verified and
the store and the service exist.

```
FindBySlug("master")
  not found        -> create it, with the derived issuer
  found, prod      -> if the stored issuer differs from the derived one, refuse the boot
  found, dev       -> if it differs, Reissue and log both values at warn
```

The seed reads and writes only the issuer. It never touches `status`: an
operator who disabled the master realm did so on purpose, and a boot step that
quietly re-enabled it would undo a deliberate act with no trace.

Both branches go through one entry point on `RealmService` — the same one that
skips the reserved-slug rule — so `Reissue` stays reachable from exactly one
caller in this slice.

The realm is created with slug `master`, display name `Master`, status
`active`, and issuer `{public_url}/realms/master`, through the seed's own
entry point on `RealmService` rather than through `Create` — `Create` refuses
reserved slugs, and `master` is the first name on that list.

It is a boot step and not an `INSERT` in a migration, for a reason that only
becomes visible in slice 2: the master realm needs a signing key encrypted with
the master key, which is Go, not SQL, and could not be written in four dialects
anyway.

### Why production refuses instead of correcting

A stored issuer that disagrees with the current `public_url` means every client
will reject the discovery document, byte for byte, and every token this process
signs. Booting into that state and finding out from support is worse than not
booting.

That creates a chicken and egg during a legitimate domain migration: the
operator cannot start the process to fix the thing that stops it from starting.
The recovery is a manual `UPDATE` against the database, stated honestly in the
documentation and in the refusal message itself rather than hidden. That is the
whole of it for this slice: `aegisd realm reissue` — a subcommand that would do
the same thing properly, without the server being up, in the shape
`aegisd migrate` already has — is named here only so it is not reinvented, and
is deliberately not built. Nothing in this slice depends on it existing.

### Why development re-derives

`developmentPublicURL()` derives the URL from the listener, so changing the dev
port leaves the stored issuer stale, discovery stops matching, and nothing
about the symptom points at the cause. Under the dev profile the seed rewrites
it and says so loudly.

The check covers the master realm only. Auditing every realm's issuer is a
diagnostic command, not startup work.

## The CLI

`cmd/aegisd/main.go` keeps its current shape: build the configuration through
the layered builder, then act. What changes is that it first asks
`internal/cli` whether `os.Args[1]` names a subcommand.

Dispatch is written by hand. Not aesthetics: Go's `flag` package stops parsing
at the first non-flag argument, so handing `migrate --dev` to the existing
`parseFlags` yields zero flags and swallows the `--dev` silently. The
subcommand is stripped before the remaining arguments reach the builder. A
command library would also bring a second flag system alongside the layered
builder that already exists.

| Command | Runner call | Exit |
|---|---|---|
| `aegisd migrate` | `Migrate` then `VerifySchema` | 0 on success, 1 on failure |
| `aegisd migrate status` | `SchemaVersion` and `Latest` | 0 when current or ahead, 1 when behind, 2 when dirty |
| `aegisd migrate force <version>` | `ForceVersion` | 0 on success, 1 on failure |
| no subcommand | serve | unchanged |

The subcommand must be the **first** argument. `aegisd --dev migrate` is not a
migration — the first token starts with `-`, so everything is treated as server
flags and the process serves. This is the usual convention and it keeps the
rule to one line, but it is a rule someone will trip over, so it gets a test
and a sentence in the documentation rather than being left to be discovered.

`migrate force` takes one argument: a non-negative integer. Anything else
fails with usage before the database is opened. `ForceVersion` already takes an
`int`, so the parse is `strconv.Atoi` plus a range check.

`migrate status` exiting non-zero when the schema is behind is what makes it
usable as a deployment gate — an init container or a pipeline step that fails
before any replica starts.

Every subcommand validates the whole configuration, not just the `database`
section. A configuration that migrates but cannot boot is a trap: the DBA
applies the schema, everything looks right, and the service then refuses to
start on a `public_url` nobody validated.

Subcommands open the database and nothing else — no HTTP server, no
certificates, no health registry. They do not go through `application.New`.

### The config-to-options translation moves

`setDatabase` currently holds twenty-five lines translating `configs.Database`
into `database.Options`. The subcommands need the same translation, and a
second copy is the kind of duplication that diverges in silence: somebody adds
a field, updates the wiring, misses the command, and migrations start running
with different TLS or pool settings than the server uses.

It moves to one exported function that both call. This is the same class of
divergence the forced-parameter parity canary already exists to catch.

### The `SchemaDirtyError` message

`internal/infra/database/migrate.go` deliberately does not name a recovery
command, because none existed and pointing an operator at a non-existent
command mid-incident is worse than naming nothing. With `aegisd migrate force`
shipping in this slice, the message names it.

## Engine version floors

The `CHECK` constraint decision moves the MySQL floor.

`internal/infra/database/mysql.go` currently enforces major 8, so 8.0.0 passes.
MySQL parsed and then silently discarded `CHECK` constraints until 8.0.16 — the
`CREATE TABLE` succeeds, the constraint does not exist, and no error is raised
anywhere. A customer on 8.0.13 would get a `realms` table whose status column
accepts anything.

The floor becomes 8.0.16, which means `parseVersion` has to read the patch
level; today it reads only the leading major and minor.

| Engine | Floor | Why |
|---|---|---|
| Postgres | 13 | unchanged — `gen_random_uuid()` without an extension |
| MySQL | 8.0.16 | changed from 8.0 — `CHECK` is silently ignored below it |
| MariaDB | 10.6 | unchanged — `CHECK` honoured since 10.2 |
| SQLite | compiled in | not enforceable; the binary ships 3.53 |

## Concurrency

Postgres takes an advisory lock and MySQL takes `GET_LOCK`, both session
scoped, which is why `db.migrator()` already opens a dedicated connection with
`MaxOpen(1)` and no `ConnMaxLifetime` — a recycled connection would drop the
lock mid-DDL and let a second replica in.

golang-migrate's SQLite driver does not take a database lock at all; its `Lock`
is an in-process `atomic.Bool`. Two processes against the same file are
unprotected. In practice SQLite cannot serve replicas anyway, so this is not a
gap to close — it is stated so nobody later assumes a protection that is not
there.

## Operational consequences

### The startup probe budget is now too small

`deploy/k8s/base/deployment.yaml` sets `startupProbe` to `periodSeconds: 2`
with `failureThreshold: 30` — a 60-second budget. With migrations running
inside `New` under a five-minute timeout, a slow first migration gets the pod
killed mid-DDL, and the next boot finds a dirty schema that needs
`aegisd migrate force`. The check meant to protect the schema would be
manufacturing the incident it exists to prevent.

`failureThreshold` goes to 180, making the budget six minutes and leaving the
migration timeout inside it. The liveness and readiness probes do not change.

This is the argument for the alternative deployment shape, and the
documentation says so: `on_boot: false` plus an init container running
`aegisd migrate` moves the work out of the pod's startup path entirely.

### The dev database already exists on disk

`aegis.dev.db` is created by the dev profile and gitignored. The first boot
after this slice migrates it. Nothing to do, but the first `make run` will take
measurably longer than the previous one and that is expected.

### `.gitignore` silently swallows the renamed package

This one bites before anything else does. `.gitignore` has a bare `aegisd`
entry, meant for the binary `go build` drops in the repository root. A pattern
with no slash matches at any depth, files and directories alike — so
`cmd/aegisd/` would be ignored, `git add` would skip it, `git status` would
show nothing, and the build would break for everyone who clones.

Verified, not assumed. The entry becomes `/aegisd`, which is what it always
meant.

## Testing

### Unit

| Package | What is proven |
|---|---|
| `internal/migrations` | `For` roots at the dialect directory; `Latest` returns the maximum and refuses an empty directory rather than returning zero |
| `internal/migrations` | **Parity**: the four directories hold the same set of versions, failing with the missing version and the directory it is missing from |
| `internal/migrations` | **One statement per file**: every `.up.sql` holds exactly one statement, because `MultiStatements=false` makes a second one a MySQL-only failure |

The statement count is not a SQL parse. Comment lines are stripped, the rest is
trimmed, and the file must contain exactly one `;`, as its last non-whitespace
character. That rule is sound for DDL we author and wrong for SQL in general —
a semicolon inside a string literal would fool it. It stays this way on
purpose: a migration that needs a semicolon in a literal is a migration worth
looking at by hand.
| `internal/configs` | `migrate` defaults; positive timeout; non-negative lock timeout; missing section reported, not dereferenced |
| `internal/infra/configbuilder` | the three environment variables and the flag land, and an absent flag overwrites nothing |
| `internal/domain/realm` | slug regex at both boundaries and each reserved word; `New` derives the issuer; `Rehydrate` does not; no path mutates id, slug, issuer, or createdAt |
| `internal/repository` | mapper round-trip, including UTC conversion |
| `internal/repository` | `Timestamp` scans a `time.Time`, a `string` and a `[]byte`, converts each to UTC, and errors on anything else instead of yielding a zero time |
| `internal/repository` | `Timestamp` round-trips through a real `STRICT` table with a `TEXT` column — a unit test, not an integration one, because the SQLite engine is compiled into the binary |
| `internal/service` | `List` clamps the limit and defaults to excluding archived; `Archive` sets the status; `Create` refuses each reserved slug while the seed path accepts `master`; against a fake repository |
| `internal/cli` | dispatch: a subcommand is recognised and stripped, `--dev` after it survives, an unknown subcommand fails with usage |

The parity test is the one that earns its place. Somebody adds `0007` to three
directories and misses `mariadb`; every engine job stays green, because
golang-migrate applies what it finds and stops without error. The customer on
MariaDB is who discovers it. Each engine's integration test also asserts the
final version rather than only that migration returned no error — the second
net, for the day someone adds a fifth directory and forgets the canary.

### Integration, tagged and on all four engines

- Migration against an empty database produces `realms` with every constraint,
  asserted by inserting rows that must fail: a bad status, a duplicate slug, a
  duplicate issuer, a slug over 63 characters.
- The `CHECK` is proven to be enforced and not merely declared — this is the
  assertion that would have caught the MySQL floor.
- Repository round-trip through a real engine, including that a UUIDv7 written
  as text reads back identically on Postgres, where the column is `uuid`.
- `Timestamp` round-trips at microsecond precision on all four, and comes back
  in UTC from a connection whose session time zone is not UTC. This is the
  assertion that would have caught the SQLite scan failure.
- The unique-violation translation produces `ErrSlugTaken` and `ErrIssuerTaken`
  on each of the four engines. The dialect error table is the most
  engine-specific code in the slice and gets the most engine coverage.
- `InTx` rolls back both writes when the callback returns an error.
- Running the migration twice is a no-op.
- `VerifySchema` refuses a schema behind and tolerates one ahead. The "ahead"
  case is built by forcing the control table past `Latest`.

### Boot, in `test/integration`

The existing `start(t, ...)` helper launches the server and waits for
readiness. A subcommand is a one-shot process that must exit, so the suite
gains a second helper alongside it — same environment construction, but it runs
to completion and returns the exit code and the combined output. The two share
the environment builder rather than duplicating the Postgres container setup.

Cases, following the existing shape:

- Booting on a fresh database creates the schema and the master realm.
- Booting a second time changes nothing — same realm id.
- `DATABASE_MIGRATE_ON_BOOT=false` against an empty database refuses to boot,
  and the message names `aegisd migrate`.
- Under the dev profile, a changed `PUBLIC_URL` rewrites the master issuer;
  under prod, the same change refuses the boot.
- `aegisd migrate` against an empty database exits 0 and the server then boots
  with `on_boot=false`.
- `aegisd migrate status` exits 1 before migrating and 0 after.

The dev-versus-prod issuer pair is the important one: a test that only asserts
production refuses does not fix polarity, and an inverted condition would leave
production silently re-deriving the issuer on every boot.

## Open, and deliberately not resolved here

- **Savepoints.** `InTx` nested inside `InTx` reuses the outer transaction. If
  a caller ever needs partial rollback, that is a design decision with a real
  consumer in front of it, not a guess made now.
- **`aegisd realm reissue`.** Named because production refusing a divergent
  issuer needs an out-of-band fix. Not built; the interim recovery is a manual
  `UPDATE`, documented as such.
- **Legal erasure.** Archiving keeps realm data indefinitely. A real erasure
  requirement needs physical deletion plus a burned-names table, and that
  crosses the realm boundary — the only global uniqueness in the system so far.
